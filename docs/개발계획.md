작성일: 2026-11-02. 순서는 **API 명세 합의 → 기술 검증 → 구현**이다. 검증이 끝나기 전에는 제품 코드를 만들지 않는다.

- API 명세: [API_명세.md](API_명세.md)
- 기획 근거: 기획서, 기능명세서 2026-11-03 저장본 (5장 AI-01~06, 6장 오류율 기준)
- 백엔드 근거: `commute-study-backend`의 `Feat/#3` 브랜치 `V1__init_schema.sql`

## 1. 현재 상태

| 레포 | 상태 |
| --- | --- |
| `commute-study-backend` | Spring Boot 4.1.2, Java 21, Supabase(PostgreSQL), Railway. 기능 코드 없음. `Feat/#3` 브랜치에 Flyway 초기 스키마가 있고 `develop` 머지 전이다. 스키마가 들어오며 `ddl-auto`는 `validate`로 바뀌었다 |

## 2. 구조

```text
앱 ──▶ Spring 백엔드 ──▶ AI 서버 (FastAPI) ──▶ LLM API
          │                   │
          ▼                   └─ 파일은 서명 URL로 내려받음
     Supabase (DB·파일)
```

| 결정 | 이유 |
| --- | --- |
| AI 서버는 Python으로 분리 | 기획서 기술 스택과 팀 레포 구조대로다. PDF·PPT 처리 라이브러리도 Python이 편하다 |
| AI 서버에 DB를 두지 않는다 | 입력을 받아 결과를 돌려주는 함수처럼 만든다. 상태 전이는 백엔드 한 곳에서 관리한다 |
| 앱은 AI 서버를 직접 호출하지 않는다 | API 키, 횟수 제한, 인증을 백엔드에서 한 번에 처리한다 |
| 긴 작업도 일반 HTTP로 호출한다 | 백엔드가 `@Async` 스레드에서 호출하고 끝까지 기다린다. 큐와 콜백을 만들지 않는다 |
| 단원 전체를 문맥으로 넣는다 | 단원이 작아서 벡터 DB가 필요 없다 |

**넣지 않는 것:** Redis, Celery, LangChain, 벡터 DB, 공용 LLM 추상화 계층. 긴 작업이 타임아웃으로 실제로 실패하면 그때 작업 큐를 검토한다.

### 기술 스택

| 영역 | 선택 |
| --- | --- |
| 서버 | Python 3.13, FastAPI, uvicorn, Pydantic |
| LLM | OpenAI Python SDK, Responses API (`responses.parse`로 구조화 출력, 스트리밍) |
| PDF | pypdfium2 (쪽별 텍스트 추출, 스캔 쪽 이미지 렌더링) |

| 이미지 | Pillow (렌더링 결과와 PNG 크기 줄이기) |
| 패키지 | venv + `requirements.txt` |
| 테스트 | pytest |
| 배포 | Railway, Dockerfile. 백엔드와 같은 프로젝트·환경에 두고 내부망만 사용 |

## 4. 단계별 계획

### 0단계. API 명세 합의 (1일)

1. 백엔드 담당과 [API_명세.md](API_명세.md)를 리뷰한다. 아래 "백엔드와 맞출 것"을 함께 정한다.
2. FastAPI 뼈대와 mock 응답을 올린다. 명세 그대로의 고정 JSON을 돌려주는 서버다.
3. Railway에 mock을 배포해, 백엔드가 LLM 없이 먼저 연동을 시작하게 한다.

완료 기준: 백엔드가 Railway 내부망으로 `/health`와 mock API를 호출할 수 있다.

### 1단계. 기술 검증 (2~3일)

위험한 가정을 실제 강의자료로 확인한다. 코드는 `eval/`의 스크립트 수준으로만 쓴다.

**준비물:** 텍스트 PDF, 스캔 PDF, PPT(.pptx), PNG를 과목이 다르게 총 3~4개. 팀원 본인의 강의자료를 쓴다. 저작권 때문에 레포에 올리지 않는다.

| # | 확인할 것 | 방법 | 통과 기준 | 실패 시 |
| --- | --- | --- | --- | --- |
| V1 | 쪽별 추출 | 형식별 1개씩 추출해 원본과 대조 | 쪽 번호 일치 100%, 본문 누락 없음 | 라이브러리 교체, 해당 형식 절삭 |
| V2 | 단원화 | 자료 3개 처리 후 사람이 경계 확인 | 쪽 범위 검증 100% 통과, 단원 80% 이상 납득 | 목차 추출을 먼저 하고 AI에 힌트로 제공 |
| V3 | 문제 품질 | 모델 3개로 각 30문제 생성 후 라벨링 | 치명 오류 30문제 중 2개 이하, 근거 대조 통과 80% 이상 | 프롬프트 수정 후 재측정, 그래도 안 되면 정답 대조 단계 추가 |
| V4 | 지연·비용 | V1~V3의 실행 기록 집계 | 기능명세서 5장 지연 목표 이내, 자료 1개 처리 비용이 예산 안 | 목표 수정, 모델 변경, 생성 수 축소 |
| V5 | 단답 판정 | 정답·오답·표기 변형·지시문 삽입 40건 | 사람 판정과 90% 이상 일치 | 정답 목록을 넓히고 판정 프롬프트 수정 |
| V6 | 스트리밍 경로 | 백엔드를 거친 SSE를 Railway에서 측정 | 첫 글자 2초 이내, 끊김 없음 | 버퍼링 설정 확인, 한 번에 받는 방식으로 후퇴 |

**V3 모델 비교:** `gpt-6-luna`, `gpt-6.1-terra`, `gpt-6.1-sol`을 같은 자료로 비교한다. 가격은 입력/출력 100만 토큰당 $0.10/$0.50, $1/$5, $2/$10이다(2026-11 기준). 라벨링은 90문제이고, 치명 오류 기준을 통과하는 가장 싼 모델을 고른다.

**라벨링 방식:** 문제, 정답, 해설, 근거 쪽을 CSV로 내보내고 사람이 치명 / 경미 / 정상으로 표시한다. 치명 오류 기준은 기능명세서 6장과 같다.

완료 기준: V1~V6 결과를 `eval/결과.md`에 기록하고, 다음을 확정한다.

- 기능별 모델
- 기능명세서 5장 지연 목표를 실측값으로 갱신
- API 명세 v1.0

### 2단계. 구현

| 순서 | 내용 | 예상 |
| --- | --- | --- |
| 1 | 공통 기반 (LLM 호출, 시간 상한, 에러) | 0.5일 |
| 2 | AI-01 추출·OCR·단원화 | 2일 |
| 3 | AI-02 생성·검증 | 2일 |
| 4 | AI-03, AI-06 | 1.5일 |
| 5 | AI-05 스트리밍 | 1.25일 |

예상에는 기능마다 코드 테스트, 평가 세트 작성과 실행, 백엔드 연동 확인이 들어 있다 (5장). 기능별 작업 분해는 [기능별_개발계획.md](기능별_개발계획.md)에 있다. 1단계에서 만든 추출 코드와 프롬프트 초안을 그대로 가져오므로, 실제로는 조금 줄어들 수 있다.

순서마다 mock을 실제 구현으로 교체하고 백엔드와 바로 연동한다. 검증 로직(`validate.py`)처럼 분기가 있는 코드에는 pytest를 붙인다. 프롬프트는 LLM 호출 없는 테스트로 검증할 수 없으므로 `eval/`로 확인한다.

### 3단계. 품질 검수와 시연 준비 (2일)

1. 100문제 검수: 치명 오류 5개 이하면 통과, 목표는 3개 이하.
2. 프롬프트 수정 후 재측정.
3. 시연 자료는 미리 처리해 둔다. 현장에서 생성을 기다리지 않게 한다.
4. 시연용 비상 데이터를 준비한다. AI 서버가 실패해도 미리 만든 문제로 진행할 수 있다.

## 5. 검증 방식

1단계 "기술 검증"은 개발 전에 한 번 하는 가능성 확인이다. 이 장은 2단계 개발 내내 하는 검증이다. 기능은 아래 네 가지를 모두 통과해야 끝난 것으로 본다. 기능별 완료 기준은 [기능별_개발계획.md](기능별_개발계획.md)에 있다.

| 종류 | 확인하는 것 | 언제 | GPT API |
| --- | --- | --- | --- |
| 코드 테스트 | 검증 규칙, 경계 보정, 에러 변환, 스트리밍 형식 | 커밋마다. PR은 GitHub Actions가 자동 실행 | 쓰지 않는다. 가짜 LLM 함수로 대신한다 |
| 평가 | 실제 모델 출력의 품질, 지연, 비용 | 기능을 처음 만들 때, 프롬프트·모델·추론 강도를 바꿀 때 | 쓴다 |
| 연동 확인 | 백엔드를 거친 호출, Railway 배포 상태 | mock을 실제 구현으로 바꿀 때, 배포 후 | 기능별 1~2회 |
| 사람 검수 | 정답 오류처럼 자동으로 못 잡는 품질 | 1단계 V3, 3단계 100문제 | 문제를 만들 때만 |

### GPT API가 필요한 때

- **코드 테스트와 CI에는 필요 없다.** 키를 CI에 넣지 않고, 테스트가 실수로 실제 API를 부르지 않게 LLM 호출을 가짜 함수로 바꾼다.
- **프롬프트를 만들고 고치는 일, 평가, 연동 확인에는 필요하다.** 실제 모델 출력을 봐야 판단할 수 있어서, 1단계부터 3단계까지 계속 쓴다.
- **백엔드·앱 개발에는 필요 없다.** 그쪽은 mock 서버를 쓴다.
- 키는 AI 담당 로컬 `.env`와 Railway 환경변수에만 둔다.
- 비용은 8장 예산의 "개발 중 테스트 $25"에서 쓴다. 평가 스크립트는 실행 전에 예상 호출 수를 출력하고, 끝나면 실제 토큰과 비용을 기록한다.

### 평가 세트 (`eval/`)

| 기능 | 세트 | 레포에 올리는지 |
| --- | --- | --- |
| AI-01 | 1단계에서 쓴 강의자료 3~4개 | 자료와 결과 원문은 올리지 않는다 (저작권). 지표 요약만 |
| AI-02 | 같은 자료의 단원 3개, 단원당 30문제 | 문제 CSV는 자료 문장이 들어 있어 올리지 않는다 |
| AI-03 | 직접 만든 판정 사례 40건 | 올린다 |
| AI-04 | 직접 만든 답안 10건 | 올린다 |
| AI-05 | 질문 12개 (자료 안 6, 자료 밖 3, 공부와 무관 2, 지시문 삽입 1) | 질문만 올린다 |
| AI-06 | 세션 사례 6개 | 올린다 |

로컬 전용 자료는 `eval/data/`에 두고 `.gitignore`로 막아 두었다.

### 다시 돌리는 규칙

- 프롬프트, 모델, 추론 강도를 바꾸는 PR은 해당 기능 평가를 다시 돌리고 결과를 PR 본문과 `eval/결과.md`에 붙인다.
- 품질 지표가 이전보다 나빠지면 머지하지 않는다. 지연이나 비용만 나빠졌다면 이유를 적고 판단한다.
- 실제 출력에서 검증 규칙에 걸린 사례가 나오면 코드 테스트에 추가한다.

### 배포 후 확인

## 7. 구현 주의사항

**OpenAI API**

- Chat Completions가 아니라 공식 권장인 Responses API를 쓴다.
- 구조화 출력은 `client.responses.parse(model=..., input=..., text_format=모델클래스)`로 받고 `response.output_parsed`를 읽는다.
- 스키마는 모든 필드가 필수이고, 없을 수 있는 값은 null을 허용하는 형태로 쓴다. 보기 개수 같은 조건은 스키마에 기대지 않고 `validate.py`가 확인한다.
- 결과를 읽기 전에 `status`가 `incomplete`인지, 응답이 `refusal`인지 확인한다.
- SDK 자동 재시도는 끈다(`max_retries=0`). 재시도는 `llm.py`가 API 명세의 시도 횟수와 서버 시간 상한대로 처리한다. 켜 두면 실제 호출 수가 명세보다 늘어나고 `attempts`도 틀어진다.
- `temperature`, `top_p`는 보내지 않는다. 추론 강도를 쓸 때는 지원되지 않고, 품질 조절은 `reasoning.effort`로 한다.
- `gpt-6-luna`와 `gpt-6.1-terra`는 effort를 `none`까지 낮출 수 있고, `gpt-6.1-sol`은 `low`가 최저다. 지연과 비용에 직접 영향을 주므로 V4에서 기능별로 정한다.
- 프롬프트 캐시는 1,024토큰 이상에서 동작하고 기본 유지 시간은 30분이다. 캐시 읽기는 `gpt-6.1-sol`과 `gpt-6.1-terra`에서 입력가의 0.05배, 쓰기는 1.25배다. 고정 내용을 프롬프트 앞에 두고 효과는 AI-05에서 실측한다.
- API 키는 `OPENAI_API_KEY` 환경변수로만 다룬다.

**Railway**

- 내부 주소에는 포트를 포함한다: `http://commute-study-ai.railway.internal:8000`
- 2025-10-16 이후 만든 환경은 내부 도메인이 IPv4·IPv6를 모두 쓰고, 이전 환경은 IPv6만 쓴다. uvicorn 바인딩(`::`)과 헬스체크는 V6에서 실제로 확인한다.
- 로컬 macOS에서는 `::`로 띄우면 IPv4(`127.0.0.1`) 요청을 받지 않았다. 리눅스 컨테이너는 기본 설정에서 IPv4도 받지만, Railway에서 직접 확인해야 한다.

**보안**

- 내부 키는 상수 시간 비교로 확인한다.
- 파일 URL은 Supabase 호스트만 허용하고, 다운로드는 30MB에서 끊는다.
- 쪽수를 먼저 확인한 뒤 본문을 처리한다.
- 로그에 자료 본문과 답안을 남기지 않는다. API 키는 커밋하지 않는다.

## 9. GitHub 작업 순서

백엔드의 `CONVENTION.md`를 따른다. 레포가 비어 있어서 처음에 한 번 설정이 필요하다.

1. 최초 커밋을 `[init]` 형식으로 올리고 `develop` 브랜치를 기본 브랜치로 지정한다.
2. 아래 이슈를 만들고, `Feat/#이슈번호` 브랜치에서 작업해 `develop`으로 PR을 보낸다.
3. PR은 GitHub Actions의 코드 테스트가 통과해야 머지한다. 프롬프트·모델을 바꾼 PR은 평가 결과를 본문에 붙인다 (5장).
4. AI는 혼자 담당이라 리뷰 승인 없이 CI 통과 후 Merge commit으로 머지하고 작업 브랜치를 지운다.
5. 배포는 `main`에서 한다. Railway는 `main`을 배포하고, 배포할 때 `develop` → `main` PR을 만들어 머지한다. `main`에는 직접 push하지 않는다.

| 브랜치 | 역할 |
| --- | --- |
| `develop` | 기본 브랜치. 작업 PR이 모이는 곳 |
| `main` | Railway 배포 브랜치. `develop` → `main` PR로만 바뀐다 |
| `{Type}/#{이슈번호}` | 작업 브랜치. `develop`에서 만들고 머지 후 지운다 |

| 단계 | 이슈 제목 |
