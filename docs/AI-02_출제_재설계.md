# AI-02 출제 재설계: 자료 양에 맞춘 문제 수

작성일: 2026-11-06. 상태: **11-07 팀 결정으로 채택, 구현 완료 (#41).** 출제 계획 프롬프트는 `app/prompts/AI-02-PLAN.md`, 코드는 `app/pipelines.py`·`app/validate.py`, 실측은 `eval/결과.md` 11-07.

구현하면서 바뀐 점:

- `capacity`는 요청한 유형으로 낼 수 있는 수다. 어떤 유형의 포인트가 모자라면 다른 유형이 요청 수를 넘겨 채운다. 유형 비율 때문에 총수가 줄지 않게 하기 위해서다.
- 탈락한 포인트를 다시 만드는 기준 시간을 20초에서 10초로 줄였다. 시간 안에 못 끝내도 이미 만든 문제는 남는다.
- 객관식 보기 중복 검사가 기호를 지워서 `plain`과 `<<plain>>`을 같은 보기로 보던 문제를 고쳤다.

## 1. 왜 바꾸나

지금은 단원마다 40문제를 요청하고, 모델이 한 번에 문제를 만든다.

| 문제 | 실측 (eval/결과.md 11-06) |
| --- | --- |
| 개념이 적은 단원에서 40문제를 채우려고 자료 문구를 묻는다 | "항목의 제목에 again이 포함되어 있다" 같은 문제가 247문제 중 47문제. 1,074자 단원은 40문제 중 20문제 |
| 그런 문제를 금지하면 40문제를 못 채운다 | 같은 단원들이 27~38문제 |
| 같은 내용을 말만 바꿔 여러 번 묻는다 | "함수에 배열을 전달하는 방식은?"과 "배열을 함수에 전달하는 방식은?" |
| 근거 문장을 모델이 문제마다 다시 고른다 | 근거 대조 탈락이 단원당 10~23개. 다시 만드는 호출이 늘어 단원당 11~12회 호출 |

40문제를 채우는 게 목표가 되면 품질이 떨어진다. **자료가 받쳐 주는 만큼만 좋은 문제를 만드는 것**을 목표로 바꾼다.

## 2. 방식: 출제 계획 → 출제

```text
단원 쪽 텍스트
   │
   ▼
① 출제 계획 (LLM 1회)        물을 가치가 있는 "출제 포인트" 목록을 뽑는다
   │
   ▼
② 코드                        근거 대조, 중복 제거, 만들 수 있는 문제 수 계산, 포인트마다 유형 배정
   │
   ▼
③ 출제 (유형별 병렬)          배정된 포인트마다 문제 하나. 근거는 포인트의 것을 그대로 쓴다
   │
   ▼
④ 코드 검증                   형식, 자료 문구 표현, 중복. 탈락한 포인트만 한 번 다시 만든다
```

### ① 출제 계획

포인트는 "학생이 시험 전에 확인해야 할 사실 한 가지"다. 정의, 동작, 차이, 이유, 조건, 코드 결과 중 하나다.

포인트마다 이 값을 받는다.

| 필드 | 뜻 |
| --- | --- |
| `statement` | 포인트를 한 문장으로 쓴 참인 명제 |
| `source_page`, `evidence_quote` | 근거 쪽과 근거 문장(글자 그대로) |
| `importance` | `core`(중심 개념) / `minor`(보조) |
| `types` | 이 포인트로 좋은 문제를 낼 수 있는 유형 (OX, MC, SHORT) |

뽑지 않는 것: 제목·목차·쪽 표시, "어떤 표현이 나온다", 수업 안내, 이름만 나열된 항목, 자료만으로 참·거짓을 못 가리는 내용. 전문은 `app/prompts/AI-02-PLAN.md`.

### ② 만들 수 있는 문제 수

```text
만들 수 있는 문제 수 = min(40, Σ 포인트별 문제 수)
  core 포인트:  고른 유형 수만큼 (최대 3)   예: OX·MC·SHORT 다 되면 3문제
  minor 포인트: 1문제
```

같은 포인트를 유형을 바꿔 묻는 것은 반복이 아니라 다른 각도의 확인이다. 이 식은 시작값이고, 검수 결과를 보고 조정한다.

**유형 배정:** 요청한 유형 비율(사전 생성은 균등)을 지키되, 포인트가 고른 유형 안에서만 배정한다. 같은 포인트가 같은 유형으로 두 번 나오지 않게 하고, 아직 쓰지 않은 포인트와 core 포인트를 먼저 쓴다. 단답이 되는 포인트가 적으면 단답이 적어진다.

### ③ 출제

지금 프롬프트(`AI-02.md`)에서 바뀌는 점이다.

- 입력에 배정된 포인트 목록(번호, 명제, 근거)을 넣고 "포인트 하나당 문제 하나, 그 포인트만 묻는다"로 바꾼다.
- 모델이 근거 문장을 다시 고르지 않는다. 포인트의 근거를 코드가 붙인다. 근거 대조 탈락이 출제 단계에서 사라진다.
- OX의 O/X 비율, 객관식 오답 규칙, 단답 정답 목록, 문체, 자료 문구 금지 규칙은 그대로다.
- 객관식 오답은 같은 단원의 다른 포인트에서 가져와도 된다고 명시한다.

## 3. 실험 결과

`eval/try_plan.py`, `gpt-6.1-terra` low, 출제 계획(①)만 실행

| 단원 | 글자 | 포인트 (core) | 만들 수 있는 문제 | 계획 시간 | 계획 비용 | 지금 방식 결과 |
| --- | --- | --- | --- | --- | --- | --- |
| Arrays | 1,074 | 6 (6) | 11 | 6초 | $0.003 | 27 (말만 바꾼 반복 다수) |
| String Object | 973 | 10 (8) | 20 | 8초 | $0.004 | 36 |
| Pointer | 3,589 | 9 (8) | 21 | 10초 | $0.006 | 29 |
| Overriding in Inheritance | 5,799 | 26 (18) | 40 | 20초 | $0.011 | 38 |

- 포인트는 개념 중심으로 정확했다. 예: "Static array는 크기를 바꿀 수 없다", "p가 x를 가리킬 때 *p = 7은 x의 값을 7로 바꾼다".
- 첫 초안은 포인트를 너무 크게 묶고(4~13개) 객관식을 한 번도 고르지 않았다. "잘게 나눈다", "오답은 같은 단원의 다른 개념을 써도 된다"를 넣어 고쳤다.
- "예제에서", "제시된 결과에서" 같은 표현이 남아 있어 금지 목록에 더했다 (재측정 전).
- 슬라이드 1~4천 자 단원은 좋은 문제가 10~20개 수준이다. 40문제는 6천 자 안팎부터 채워진다.

## 4. 시간과 비용

| 항목 | 지금 | 재설계 (추정) |
| --- | --- | --- |
| LLM 호출 | 단원당 6~12회 (근거 탈락으로 재생성이 많다) | 계획 1회 + 출제 3~5회 |
| 시간 | 18~40초 | 계획 6~20초 + 출제 15~25초 = 25~45초. 서버 상한 55초 안이지만 큰 단원은 여유가 적다 |
| 비용 | 단원당 $0.04~0.08 | 계획 $0.003~0.011 + 출제(문제 수에 비례). 문제가 적은 단원은 싸진다 |

큰 단원에서 55초가 빠듯하면 계획 단계를 `gpt-6-luna`로 바꿔 비교한다.

## 5. 팀이 정해야 할 것

이 방식은 기능명세서의 "단원당 40문제"와 다르다. 기획 결정이 필요하다.

| # | 정할 것 | 제안 |
| --- | --- | --- |
| 1 | 단원당 문제 수 | "단원당 최대 40문제, 자료 양에 맞춰 AI가 정한다" |
| 2 | 진도 계산 | 푼 문제 ÷ 그 단원의 문제 수 (지금은 ÷ 40) |
| 3 | 유형 비율 | "균등"은 가능한 범위에서. 단답으로 물을 포인트가 적으면 단답이 적다 |
| 4 | 추가 생성 | 자료를 다 쓴 단원은 추가 생성하지 않고 이미 나온 문제를 다시 낸다 (재출제 순서는 그대로) |
| 5 | 작은 단원 | 문제가 10개 안팎인 단원이 생긴다. 통학 30분이면 한 단원을 다 풀고 다음 단원으로 넘어간다 ('이어서 더 풀기'와 같은 흐름) |

## 6. API 영향 (합의 후 적용)

요청 형식은 그대로다. 응답에 필드 하나를 더한다.

```json
{
  "questions": [ ... ],
  "shortfall": [ ... ],
  "capacity": 21,
  "rejected": { ... },
  "meta": { ... }
}
```

- `capacity`: 이 단원 자료로 만들 수 있다고 판단한 최대 문제 수. 요청 수보다 적으면 `shortfall`이 생겨도 다시 요청하지 않는다.
- `shortfall`은 지금처럼 요청 대비 모자란 수다. `capacity`보다 적게 나온 경우(생성 실패)만 다시 요청할 가치가 있다.
- 추가 생성 요청에도 `capacity`가 온다. 이미 있는 문제 수가 `capacity` 이상이면 백엔드는 추가 생성을 부르지 않는다.

## 8. 열린 질문

- core 포인트를 최대 3문제로 묻는 게 반복으로 느껴지는지: 검수에서 확인한다.
- 계획을 매 추가 생성 때 다시 만들지: AI 서버는 상태가 없어서 다시 만든다. 이미 있는 문제의 포인트는 `excludeStems`와 비교해 건너뛴다.
- 난이도: 사전 생성 난이도 구성(기획 질문)이 정해지면 포인트에 난이도 가능 범위를 더할지 본다.
